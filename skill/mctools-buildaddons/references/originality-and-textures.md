# Originality, textures and licensing

Contents: 1. Originality rules · 2. When the user asks to copy something · 3. What may be reused · 4. Generating textures · 5. Wiring textures into content · 6. Texture technical rules · 7. Custom art (entities, bigger art, user files) · 8. No filler files

## 1. Originality rules

The user wants a working add-on for **their** idea, not a re-skin of somebody else's. Follow these habits:

- Start from the user's concept and design your own take: own item/block/command names, own numbers, own mechanics wording, own code structure and comments. If a feature is common (a shop menu, a home system), implement it fresh from the API reference; do not reproduce a known add-on's file layout, identifiers or text.
- Pick a distinctive namespace and identifiers (`gemquest:ruby_ore`, not generic ones like `custom:item1`, and never another creator's namespace or brand).
- Do not reuse names, lore, characters, logos or art from games, shows or brands (Pokémon, Marvel, Mojang's marketplace partners, etc.). Offer an original theme with a similar feel instead.
- Do not copy code from other add-ons or Marketplace packs, and never decompile or "borrow" a pack file. Learning from official documentation and MIT-licensed samples (Microsoft `minecraft-scripting-samples`, Bedrock Wiki code samples are MIT) is fine: understand the pattern, then write your own implementation for the user's feature.
- Never use Minecraft's own textures, models, sounds or sprites as your add-on's assets (they belong to Mojang and cannot be redistributed in a pack). Referencing a vanilla texture path from a form button icon or reusing a vanilla shortname the game already ships is fine; shipping a copy of the file is not.

## 2. When the user asks to copy something

Typical wording: "buat seperti addon X", "same as the Marketplace pack", "copy this addon". Respond briefly and keep helping:

1. Say you will not replicate another creator's add-on 1:1, and that you will build the same **idea/feature set** with original names, art and code.
2. Ask for (or infer) the feature list: what should it do for the player? Build that.
3. If the user pastes someone else's code or files: do not paste them back with cosmetic changes. Use them only to understand the requested behavior, then write new code. If they own the code or it has a permissive license, say what license applies and keep the required notice.
4. Never remove credits or license notices from files the user is entitled to reuse.

## 3. What may be reused

| Source | OK? | Condition |
|---|---|---|
| Textures generated by `make_texture.py` | Yes | Original, CC0, recorded in the PNG metadata |
| The user's own art, sounds, models | Yes | The user states they made it or own it |
| Open-licensed art (CC0, CC-BY, MIT) | Yes | State the license; CC-BY/MIT need attribution; ask the user to supply the file, do not fetch from random sites |
| Vanilla Minecraft assets | No | Copyright Mojang; only reference vanilla shortnames/paths already in the game |
| Marketplace / other add-on assets | No | Copyright of their authors |
| Images from search engines, AI images of unknown licence | No | Unknown rights |

When third-party material is genuinely used (with permission/license), record it in a single `CREDITS.txt` in the pack root with source, author and license. Create that file **only** in that case.

## 4. Generating textures

The generators draw pixel art procedurally (math + seeded randomness) so the result is original and unique per color/seed. Styles:

- Items (transparent 16x16 icon with outline): `gem`, `ingot`, `orb`, `potion`, `sword`, `wand`
- Blocks (opaque, tile seamlessly): `stone`, `bricks`, `planks`, `ore`, `metal`, `crystal`

```bash
python scripts/make_texture.py --list
python scripts/make_texture.py item  --rp proj/my_addon_RP --namespace myaddon --id ruby --style gem --color "#d81e5b"
python scripts/make_texture.py block --rp proj/my_addon_RP --namespace myaddon --id ruby_ore --style ore --color "#d81e5b" --seed 2
python scripts/make_texture.py item  --out ./preview/ruby.png --style gem --color "#d81e5b"    # only a PNG, no registration
```

Choosing styles to match the idea: `ore` for ore blocks (stone with colored veins), `crystal` for gem blocks, `metal` for machine/tech blocks, `bricks`/`planks` for building blocks, `stone` for generic natural blocks; `gem`/`ingot` for materials, `orb` for magic items, `potion` for consumables, `sword`/`wand` for tools. Use a hex color that fits the theme; change `--seed` for a different variation of the same style. If no style matches what the user wants (a custom mob, a face, a logo), say so honestly and use section 7.

## 5. Wiring textures into content

`add_content.py` does all of this for you. When doing it by hand (verified formats, stable game):

Item definition `BP/items/ruby.json` (format_version `1.21.60`; the `components` object must exist):

```json
{
  "format_version": "1.21.60",
  "minecraft:item": {
    "description": { "identifier": "myaddon:ruby", "menu_category": { "category": "items" } },
    "components": { "minecraft:icon": "myaddon_ruby", "minecraft:max_stack_size": 64 }
  }
}
```

Registration `RP/textures/item_texture.json` (shortname → path **without** extension):

```json
{
  "resource_pack_name": "my_addon_rp",
  "texture_name": "atlas.items",
  "texture_data": { "myaddon_ruby": { "textures": "textures/items/ruby" } }
}
```

Block definition `BP/blocks/ruby_ore.json` (format_version `1.21.110`, which needs `min_engine_version` ≥ 1.21.110):

```json
{
  "format_version": "1.21.110",
  "minecraft:block": {
    "description": { "identifier": "myaddon:ruby_ore", "menu_category": { "category": "construction" } },
    "components": {
      "minecraft:geometry": "minecraft:geometry.full_block",
      "minecraft:material_instances": { "*": { "texture": "myaddon_ruby_ore", "render_method": "opaque" } },
      "minecraft:destructible_by_mining": { "seconds_to_destroy": 3 }
    }
  }
}
```

Registration `RP/textures/terrain_texture.json`:

```json
{
  "resource_pack_name": "my_addon_rp",
  "texture_name": "atlas.terrain",
  "padding": 8,
  "num_mip_levels": 4,
  "texture_data": { "myaddon_ruby_ore": { "textures": "textures/blocks/ruby_ore" } }
}
```

Display names go in `RP/texts/en_US.lang` (plus `RP/texts/languages.json` containing `["en_US"]`):

```
item.myaddon:ruby.name=Ruby
tile.myaddon:ruby_ore.name=Ruby Ore
```

Format versions are per-file schema versions; they are not the game version. Re-check them against the Bedrock Wiki "Item/Block Format History" pages when the user needs newer components.

## 6. Texture technical rules

- PNG, 8-bit RGBA or RGB. Width and height are powers of two: 16, 32, 64, 128 (256 and up only when needed; 1024 is the hard ceiling).
- Item icons: transparent background, subject inside the frame, 1px outline reads best at 16x16.
- Block textures: square, opaque, designed to tile; use `render_method` `opaque` unless transparency is needed (`alpha_test`/`blend`).
- Lowercase file names with underscores, no spaces; paths are case-sensitive on Android/Linux.
- Registered path has no extension; the file extension is `.png` (or `.tga`).
- Every PNG in `textures/items` or `textures/blocks` must be registered, and every registration must have its file (the validator checks both).
- Pack icon: `pack_icon.png`, 256x256 recommended (the scaffold generates one).
- A texture changes only when the pack is re-applied or the world reloaded; if an old texture still shows, bump the pack `version` or re-import.

## 7. Custom art, entities and user files

- **Entity textures** are not generated by these scripts. A custom mob needs a client entity definition, a geometry model and a skin that matches the model's UV layout; do these only when requested, create the skin from the model (not a random PNG), and register it in the client entity JSON (`textures`), not in `item_texture.json`.
- **User-made art**: if the user provides PNGs, copy them to `RP/textures/items|blocks/`, convert names to lowercase, check size is a power of two, and register them with a small snippet (or run `make_texture.py` for an original replacement if they have none).
- **Larger or hand-drawn art**: suggest the user draws in Blockbench/Aseprite/any editor; export PNG with the sizes above. Do not claim the generator can draw arbitrary pictures.
- **Animated textures** (flipbook) are an extra feature: only add when asked, and follow the current Bedrock Wiki "Block/Item Texture Animation" page.

## 8. No filler files

Before delivering, list the project tree and remove anything that is not used:

- Empty `.lang`, `.json`, `.js`, `.mcfunction` files and empty folders (`sounds/`, `models/`, `texts/` with nothing in them)
- Resource pack with no content (if nothing needs textures/sounds/models, there should be no RP at all)
- Demo commands/menus the user did not ask for, commented-out blocks, "TODO" stubs
- Textures that no item/block/entity references
- Extra README/LICENSE files nobody requested (a `CREDITS.txt` is only for real third-party material)

`validate_addon.py` reports empty files as errors and empty folders, content-less packs, comment-only scripts and unregistered textures as warnings.
